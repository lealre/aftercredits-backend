## This version's scope: route handler DB calls through services
The convention (documented in `CONVENTIONS.md` §1) is: handlers never call the DB
directly — always via a service method. v0.0.11 documented it and deferred the
actual refactor to here. This PR makes handlers compliant. **Behavior-preserving:
same responses, same status codes; all existing tests must still pass.**

### The 17 offending call sites (verified on `main` a435a77)
Method → add a thin service wrapper, call it from the handler instead of `api.Db.X`:

- `internal/api/titles_handlers.go:70` `api.Db.TitleExists` → `titles.TitleExists`
- `internal/api/titles_handlers.go:108` `api.Db.TitleExists` → `titles.TitleExists`

Distinct methods to wrap: `TitleExists` (titles svc), `GroupExists`,
`GroupContainsTitle`, `GetGroupById` (groups svc), `UserExists` (users svc).

### Approach
- Add thin service functions (signature mirrors the handler call, taking `db *mongodb.DB` + ctx + args) in the owning service package (`internal/services/{titles,groups,users}`). Each just delegates to the existing `db.<Method>(...)`.
- Preserve the handlers' existing error handling exactly (they already special-case `mongodb.ErrRecordNotFound` and use each service's `ErrorMap`). Don't change status codes/messages.
- Cross-domain note: `GroupContainsTitle` is a group concern used by ratings + comments handlers — put the wrapper in `groups` and import it there (already imported in those handlers).
- Keep it a pure refactor: no new endpoints, no signature changes to existing exported service funcs beyond the new wrappers.
